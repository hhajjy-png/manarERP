# جاهزية XBRL — XBRL Readiness Foundation v1

طبقة تحضيرية مستقلة تجعل manarERP **قابلًا للتوسعة نحو XBRL** دون إعادة تصميم النظام
المحاسبي عند وصول المواصفة الرسمية.

---

## ⚠ ما لا يدّعيه هذا النظام

**manarERP غير متوافق رسميًا مع QAYD ولا مع وزارة التجارة والصناعة الكويتية في هذه
المرحلة.** لا تُكتب هذه العبارة في أي شاشة، ولا في أي تقرير، ولا في أي وثيقة تسويقية.

ما بُني فعلًا: بنية بيانات وربط وتحقق ولقطات، جاهزة لاستقبال تصنيف رسمي عند نشره.

| السؤال | الجواب في v1 |
|--------|--------------|
| هل توجد Taxonomy كويتية رسمية مثبَّتة؟ | **لا** |
| هل تُفترض مواصفة QAYD أو تُخمَّن مفاهيمها؟ | **لا** |
| هل يُفترض وجود API حكومي؟ | **لا** |
| هل يُنتَج ملف XBRL رسمي؟ | **لا** |
| هل توجد وسوم (tags) حكومية مكتوبة في الشفرة؟ | **لا** |
| هل يمكن ربط حسابات المنار بمفاهيم مستقبلية؟ | **نعم** |
| هل يعمل التحقق والجاهزية بلا تصنيف حكومي؟ | **نعم** |

## الحدود المعمارية

```
دليل الحسابات ──قراءة──▶ [ طبقة XBRL ] ──كتابة──▶ جداول xbrl_* فقط
قيود اليومية  ──قراءة──▶
```

* **لا كتابة محاسبية**: لا `create`/`update`/`delete` على `accounts` أو `journal_entries`
  أو أي جدول محاسبي. مفروض باختبار ثابت يفحص شفرة الوحدة كلها
  (`__tests__/accounting.isolation.test.ts`).
* **لا منطق محاسبي مكرّر**: الأرصدة تأتي من `financialService.getTrialBalance` — ميزان
  المراجعة نفسه الذي تعرضه شاشات النظام.
* **لا قفل ولا منع**: نتيجة التحقق تقرير. خطأ `ERROR` هنا لا يمنع ترحيل قيد ولا اعتماد
  فاتورة ولا صرف راتب.
* **لا أثر على وحدة أخرى**: الرواتب، مستحقات الموظف، الشيكات، المخزون — لا شيء منها
  يقرأ هذه الجداول أو يُقرأ منها.

## البنية

```
modules/xbrl/
  xbrl.constants.ts        أكواد قواعد التحقق (ثابتة للأبد)، الحالات، الرسائل
  xbrl.types.ts            أنواع النطاق — كلها صور مقروءة
  xbrl.schema.ts           تحقق Zod (لا يقبل isOfficial في أي مخطط)
  xbrl.routes.ts           المسارات — لا PATCH/PUT/DELETE على /snapshots
  xbrl.controller.ts       طبقة رقيقة بلا منطق
  domain/
    validation.engine.ts   قواعد التحقق — دوال صافية بلا Prisma
    readiness.score.ts     حساب المؤشر — دوال صافية
  services/
    taxonomy.service.ts    سجلّ التصنيفات (isOfficial غير قابل للكتابة)
    concept.service.ts     مفاهيم التصنيف
    mapping.service.ts     ربط الحسابات
    statementMapping.service.ts  ربط بنود القوائم
    context.service.ts     سياق التقرير
    readiness.service.ts   تجميع البيانات + تشغيل التحقق
    snapshot.service.ts    اللقطات (create / list / getById فقط)
  export/
    exporter.ts            FinancialReportingExporter + XbrlExporter (حاجز)
```

### جداول قاعدة البيانات

`xbrl_taxonomies` · `xbrl_concepts` · `xbrl_account_mappings` ·
`xbrl_statement_mappings` · `xbrl_reporting_contexts` · `xbrl_snapshots`

الترحيل: `20260819120000_add_xbrl_readiness_foundation` — إضافي بحت، بلا `ALTER` على أي
جدول قائم. التراجع المنطقي: إسقاط الجداول الستة بترتيب عكسي للاعتماديات.

### الصلاحيات

`xbrl.read` · `xbrl.manage` · `xbrl.snapshot` — ثلاثة مفاتيح لا أكثر. مستقلة عن
`transactions.*` و`finreports.*`: قراءة التقارير المالية لا تمنح تعديل الربط.

## قواعد التحقق

| الكود | الشدّة | المعنى |
|-------|--------|--------|
| `ACC-001` | ERROR | ميزان المراجعة غير متوازن |
| `ACC-002` | ERROR | معادلة الميزانية لا تُغلق |
| `ACC-003` | ERROR / WARNING | حسابات مالية فعّالة بلا ربط (خطأ مع تصنيف مفعَّل) |
| `ACC-004` | ERROR | حساب فعّال بنوع غير معروف |
| `RPT-001` | ERROR | سياق التقرير مفقود أو فترته غير صحيحة |
| `RPT-002` | ERROR | فترة المقارنة غير متسقة |
| `RPT-003` | ERROR | العملة مفقودة أو بصيغة غير صالحة |
| `RPT-004` | ERROR / WARNING | بيانات الشركة ناقصة |
| `MAP-001` | ERROR | تعارض ربط (نوافذ سريان متداخلة) |
| `MAP-002` | ERROR | ربط بمفهوم من تصنيف آخر |
| `MAP-003` | WARNING | لا يوجد تصنيف مفعَّل |
| `MAP-004` | WARNING | مفاهيم مطلوبة بلا ربط |
| `MAP-005` | WARNING | ربط يتيم |
| `MAP-006` | WARNING | بند قائمة مفعَّل بلا مفهوم |
| `EXP-001` | INFO | لا تصنيف رسمي مثبَّت (الحالة الطبيعية في v1) |

**الأكواد ثابتة للأبد.** اللقطات القديمة تُقرأ بها؛ تغيير معنى كود قائم يُفسد تفسير كل
لقطة سابقة. القاعدة الجديدة تأخذ كودًا جديدًا.

### حالات الجاهزية

`NOT_READY` ← `IN_PROGRESS` ← `READY_PENDING_TAXONOMY`

**لا توجد حالة `QAYD_READY`** ولن توجد قبل استيفاء قواعد رسمية منشورة واختبارها.

## عقد التوسعة المستقبلية (المرحلة الثانية)

عند نشر ملفات ومواصفات QAYD الرسمية، يُضاف ما يلي **بلا إعادة بناء أي شيء أعلاه**:

1. **مستورد التصنيف الرسمي** — الملف الجديد الوحيد الذي يحقّ له ضبط `isOfficial = true`.
   لا مسار API قائم يفعل ذلك اليوم، وهو ما يجعل النقطة قابلة للتنفيذ بأمان لاحقًا.
   ➜ يضيف: `services/officialTaxonomyImporter.service.ts`
2. **المفاهيم الرسمية** — تُملأ في `xbrl_concepts` من ملف التصنيف، لا من قائمة مكتوبة يدويًا.
3. **قواعد التحقق الرسمية** — تُضاف كدوال جديدة في `domain/validation.engine.ts` بأكواد
   جديدة (`QYD-001`, ...). القواعد القائمة لا تُمسّ.
4. **ربط الشركة والحسابات** — بيانات، لا كود: تُدخَل من الشاشة القائمة أو تُستورد.
5. **توليد مستند XBRL** — يُملأ جسم `XbrlExporter.export`. الشرط
   `dataset.taxonomy?.isOfficial` يبدأ بالمرور من تلقاء نفسه عند تثبيت تصنيف رسمي.
6. **التحقق من المخطط (Schema validation)** — مُصدِّر إضافي أو خطوة داخل `XbrlExporter`.
7. **حزمة تصدير خاصة بـQAYD** — مُصدِّر جديد يحقّق `FinancialReportingExporter` ويُسجَّل
   في `EXPORTERS`.
8. **التكامل مع API** — **فقط** إذا وُجد API رسمي موثّق. لا يوجد اليوم عميل HTTP واحد في
   الوحدة، ويحرس ذلك اختبار ثابت.

نقطة الاستئناف الدقيقة: `export/exporter.ts` → `XbrlExporter.unavailableReason`.

## ما بقي معلَّقًا لعدم توفر مواصفات QAYD

* أكواد المفاهيم الرسمية وأسماء الـnamespaces.
* قواعد التحقق التي تفرضها الجهة (حقول إلزامية، تجميعات، dimensions).
* بنية حزمة التقديم وصيغتها (XBRL / iXBRL / ZIP).
* آلية التقديم: ملف يُرفع يدويًا أم API.
* متطلبات التوقيع أو الاعتماد الإلكتروني.
* الخريطة المرجعية بين دليل حسابات المقاولات ومفاهيم التصنيف.

كل بند أعلاه **غير مُخمَّن عمدًا**. تخمينه يعني بناء ربط سيُعاد بناؤه، وشاشة تعلّم
المستخدم أرقامًا خاطئة.
