## 2. التثبيت على جهاز جديد

1. انسخ `AlManarERP-Setup-2026.2.0.exe` إلى الجهاز الجديد.
2. شغّله. عند ظهور SmartScreen: **المزيد من المعلومات ← تشغيل على أي حال**.
3. **Next ← Install ← Finish**.

لا خطوات أخرى. لا تثبيت Node.js، ولا قاعدة بيانات، ولا نسخ ملفات يدوي، ولا إعدادات.

### ما يجري تلقائيًا أثناء التثبيت

| الخطوة | التفصيل |
|---|---|
| فحص المنصّة | يُرفض التثبيت على 32-bit أو على Windows أقدم من 10 (1809) برسالة عربية واضحة |
| فحص المتطلبات | يُفحص كل متطلب وقت تشغيل؛ الموجود يُتخطّى والناقص يُثبَّت صامتًا. **حاليًا: لا متطلبات خارجية** (§5) |
| نسخ الملفات | إلى `%LOCALAPPDATA%\Programs\Al Manar ERP` — بلا صلاحيات مسؤول |
| الاختصارات | سطح المكتب + قائمة ابدأ باسم «نظام المنار» |
| إلغاء التثبيت | مُسجَّل في «التطبيقات والميزات» |

### ما يجري عند أول تشغيل

| الخطوة | التفصيل |
|---|---|
| إنشاء مجلدات البيانات | `backups`، `backups/pre-sync`، `backups/pre-restore`، `logs`، `attachments`، `documents`، `exports` |
| نسخ قاعدة البيانات | القاعدة الحالية كاملة تُنسخ إلى `%AppData%\Al Manar ERP\data\manar.db` |
| نسخ ملفات الحالة | `sync-metadata.json` (ربط ملف Google Drive وسجلّ المزامنة) و `gdrive-account.json` |
| توليد سرّ الجلسات | `security.json` — يُولَّد محليًا لهذا التثبيت |
| هوية الجهاز | `device-identity.json` — تُولَّد جديدة لهذا الجهاز |
| ترحيلات قاعدة البيانات | `prisma migrate deploy` يُطبِّق أي ترحيل معلَّق |

**كل خطوة إضافية بحتة:** الملف الموجود لا يُستبدل أبدًا. إعادة التثبيت أو الترقية فوق تثبيت قائم لا تمسّ أي بيان مستخدم.

## 3. أين تعيش البيانات

```
%AppData%\Al Manar ERP\data\
├── manar.db                  قاعدة البيانات (كل بيانات النظام والإعدادات والقوالب والشعارات)
├── backups\                  النسخ الاحتياطية التلقائية واليدوية
│   ├── pre-sync\             نسخة أمان قبل كل مزامنة سحابية
│   └── pre-restore\          نسخة أمان قبل كل استعادة
├── attachments\              مرفقات العملاء والعقود والفواتير والموظفين…
├── documents\  exports\      مخرجات المستندات والتصدير
├── logs\                     سجلّات التشغيل والأخطاء
├── security.json             سرّ توقيع الجلسات (خاص بهذا التثبيت)
├── device-identity.json      هوية الجهاز (خاصة بهذا الجهاز)
├── gdrive-token.dat          رمز Google Drive — مُعمّى بـDPAPI لهذا المستخدم
├── gdrive-account.json       بريد الحساب المرتبط
└── sync-metadata.json        سجلّ المزامنة وربط ملف Drive
```

**لا شيء يُكتب داخل مجلد التثبيت.** بيانات المستخدم تنجو من إلغاء التثبيت
(`deleteAppDataOnUninstall: false`) ومن كل ترقية لاحقة.

## 4. المزامنة السحابية (Google Drive)

عميل OAuth مُضمَّن داخل المثبّت — المستخدم لا يُنشئ ولا ينسخ أي ملف تهيئة.

**الخطوة الوحيدة المطلوبة على الجهاز الجديد:**
النسخ الاحتياطي ← المزامنة السحابية ← **ربط حساب Google** ← تسجيل الدخول في المتصفح.

### لماذا لا يُنقل رمز الدخول تلقائيًا

`gdrive-token.dat` مُعمّى بـ**DPAPI** (Windows Data Protection API)، وهو مربوط بحساب
المستخدم والجهاز اللذين أنشآه. نقله إلى جهاز آخر يُنتج ملفًا لا يمكن فكّ تعميته
بأي حال — لا على مستوى التطبيق ولا على مستوى النظام. هذا قيد أمني في وندوز، لا نقص
في الحزمة. ربط الحساب من جديد ضغطة زر واحدة، ويستعيد الاتصال بنفس ملف Drive لأن
`sync-metadata.json` (المُرفق بالمثبّت) يحمل `lastSyncedFileId`.

### أول مزامنة بعد الربط

القاعدة المشحونة موسومة **«بذرة تهيئة»** لا «بيانات مستخدم». لذلك أول مزامنة
**تُنزّل** من Drive حصرًا ولا تستطيع الرفع فوق البيانات السحابية أبدًا — حتى لو
اختار المستخدم ذلك يدويًا (مسار الرفع يرفض البذرة صراحةً). حماية مزدوجة ضد أخطر
سيناريو ممكن: استبدال بيانات سحابية حقيقية بقاعدة مشحونة.

## 5. الاعتماديات وقت التشغيل

المتطلبات لا تُكتب يدويًا — تُستخرَج من **جداول استيراد PE** لكل ثنائي مشحون:

```bash
node scripts/analyze-runtime-deps.js     # ← build/runtime-requirements.json
node scripts/generate-nsis-prereqs.js    # ← build/installer-prereqs.nsh
```

### النتيجة الحالية: صفر متطلبات خارجية

| المكوّن | الحالة |
|---|---|
| Electron 31 (Chromium + Node.js) | **مُضمَّن** — لا يتطلب Node.js على الجهاز |
| Prisma Query Engine (أصلي، Rust) | **مُضمَّن** — يربط ساكنًا بـCRT، لا يحتاج VC++ Redistributable |
| SQLite | **مُضمَّن** داخل محرّك Prisma |
| مكتبات النظام | كلها ضمن خط أساس Windows 10/11 القياسي |

فُحص كل ثنائي `.exe`/`.dll`/`.node` مشحون. لا استيراد واحد خارج مكتبات النظام
المضمونة وعقود API Set. **الحزمة مكتفية ذاتيًا بالكامل.**

المحلّل **fail-closed**: أي استيراد لا يعرفه يُنهي البناء برمز 1 بدل أن يمرّ بصمت
ويُنتج مثبّتًا يفشل على أول جهاز نظيف.

### إذا ظهر متطلب مستقبلًا

يكفي إضافة تعريفه إلى `REDISTRIBUTABLES` في `analyze-runtime-deps.js` ووضع ملف
التثبيت في `build/prereq/`. المولّد ينتج تلقائيًا منطق «افحص ← تخطَّ أو ثبِّت صامتًا»
داخل المثبّت. وإن أُعلن متطلب بلا ملف تثبيت مُضمَّن، **يفشل البناء** — فلا يُوعَد
المستخدم بشيء لا يستطيع المثبّت الوفاء به بلا إنترنت.

## 6. بناء المثبّت

```bash
npm run dist
```

يُنفّذ بالترتيب:

| # | الخطوة | الدور |
|---|---|---|
| 1 | `build:back` | ترجمة الخدمة الخلفية + حلّ مسارات الاختصار |
| 2 | `build:front` | بناء واجهة React |
| 3 | `electron:build` | ترجمة العملية الرئيسية |
| 4 | `package:backend-deps` | تثبيت معزول لاعتماديات الإنتاج + كنس بقايا محرّك Prisma |
| 5 | `package:seed-data` | التحقق من سلامة القاعدة + تجهيز `build/seed-data` + تهيئة عميل OAuth |
| 6 | `package:analyze-deps` | فحص جداول استيراد PE ← بيان المتطلبات |
| 7 | `package:nsis-prereqs` | توليد سكربت المتطلبات للمثبّت |
| 8 | `package:repair-cache` | إصلاح ذاكرة أدوات electron-builder (§6.1) |
| 9 | `electron-builder` | إنتاج `AlManarERP-Setup-2026.2.0.exe` |

**الترتيب مُلزَم** ومُغطّى باختبار في `electron/__tests__/electronBuilderPackaging.test.ts`:
التحليل يحتاج `node_modules` ممتلئًا، وتوليد السكربت يحتاج بيان التحليل.

### 6.1 إصلاح ذاكرة أدوات electron-builder

كان بناء المثبّت **مستحيلًا على هذا الجهاز** قبل هذه الحزمة، ولم ينجح ولا مرّة منذ
17 يوليو. السبب ليس في المشروع:

يحتاج electron-builder حزمة `winCodeSign` لتشغيل `rcedit` (الأداة التي تكتب الأيقونة
ومعلومات الإصدار داخل الملف التنفيذي). الحزمة أرشيف مشترك بين المنصّات يحوي روابط
رمزية لمكتبات macOS:

```
darwin/10.12/lib/libcrypto.dylib → libcrypto.1.0.0.dylib
darwin/10.12/lib/libssl.dylib    → libssl.1.0.0.dylib
```

إنشاء رابط رمزي على وندوز يتطلب امتياز `SeCreateSymbolicLinkPrivilege` (صلاحيات
مسؤول أو «وضع المطوّر»). بدونه يخرج `7za` بالرمز 2، ويعتبره electron-builder فشلًا
قاتلًا فيتوقّف البناء — رغم أن الملفات المعطوبة تخصّ macOS ولا تُستعمل على وندوز إطلاقًا.

`scripts/repair-builder-cache.js` يفكّ الأرشيف مرّة واحدة **باستثناء شجرة `darwin/`**
إلى المسار الذي يبحث فيه electron-builder، فيتخطّى التنزيل والفكّ كليًا ولا يُنشئ
رابطًا رمزيًا أصلًا. آمن للتكرار، ولا يمسّ أي ملف في المستودع ولا في المثبّت.

> يعمل تلقائيًا ضمن `npm run dist`. على أي جهاز بناء جديد سيعمل من تلقاء نفسه
> في أول بناء — لا حاجة لتفعيل «وضع المطوّر» ولا لتشغيل البناء كمسؤول.

### حواجز أمان البناء

- **قاعدة قيد الاستخدام:** وجود أي ملف `-wal` / `-shm` / `-journal` بجوار قاعدة القالب
  يُفشل البناء. نسخ SQLite أثناء التشغيل يُنتج قاعدة مبتورة تفشل عند أول استعلام على
  جهاز المستخدم — يُكتشف عند البناء لا عنده.
- **قاعدة تالفة:** يُتحقَّق من ترويسة `SQLite format 3` والحجم الأدنى.
- **تهيئة OAuth مفقودة:** يُفشل البناء بدل إنتاج نسخة بلا مزامنة سحابية صامتًا.

## 7. تنظيف بقايا التطوير

```bash
node scripts/cleanup-dev-artifacts.js            # عرض فقط
node scripts/cleanup-dev-artifacts.js --apply    # تنفيذ
```

يحذف سكربتات التشخيص والإصلاح لمرة واحدة، ومخرجات الاختبارات المؤقتة، وبقايا نسخ
محرّك Prisma المؤقتة.

**لا يحذف** مجموعة الاختبارات الحقيقية ولا أي ملف بيانات أو مستند أو أصل تصميم.
لا شيء من هذه البقايا يدخل حزمة التثبيت أصلًا — الحذف نظافة مستودع لا شرط تشغيل.
