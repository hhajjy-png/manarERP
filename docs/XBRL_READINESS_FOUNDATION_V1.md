# XBRL Readiness Foundation v1 — جاهزية XBRL

> **الحزمة:** `feature/xbrl-readiness-foundation-v1` — **التاريخ:** 2026-08-19
> **حالة الإصدار وسجلّه:** `PROJECT_STATE.md` (هذا الملف يوثّق النطاق والحدود، لا دورة الإصدار).

---

## ⚠ إخلاء مسؤولية دائم

**manarERP غير متوافق رسميًا مع منظومة QAYD أو وزارة التجارة والصناعة الكويتية.**

لم تُفترض في هذه الحزمة أي Taxonomy كويتية رسمية، ولم يُفترض وجود API حكومي، ولم يُكتب أي وسم
(tag) أو namespace رسمي في الشفرة. ما بُني هو **بنية تحضيرية** تسمح بإضافة كل ذلك لاحقًا دون
إعادة تصميم النظام المحاسبي.

هذه العبارة جزء من العقد، لا تحفّظ إجرائي: أقصى حالة يعرضها النظام هي
`READY_PENDING_TAXONOMY` («جاهز — بانتظار تصنيف رسمي»)، ولا توجد في الشفرة ولا في الواجهة حالة
اسمها «QAYD Ready». يحرس ذلك اختبار ثابت يفحص شفرة الوحدة كلها.

---

## 1. الهدف

تجهيز manarERP ليكون **XBRL-ready**: عند صدور الـTaxonomy والدليل الفني الرسمي لـQAYD، نضيف
الـMapping والتصدير الحقيقي فوق بنية قائمة، بدل بناء كل شيء من الصفر تحت ضغط موعد نهائي.

المسار المستهدف:

```
Accounting → Financial Statements → XBRL Mapping Layer → Validation → Export
```

المرحلة الأولى بنت الحلقات الثلاث الوسطى، وتركت `Export` حاجزًا مقصودًا.

---

## 2. حدود المرحلة الأولى

| البند | الحالة |
|-------|--------|
| Taxonomy كويتية رسمية | **غير مثبَّتة** — `isOfficial` لا يُضبط من أي مسار API |
| مفاهيم QAYD | **غير مُدخلة** — الجدول يُخلق فارغًا |
| API حكومي | **غير مفترض** — لا عميل HTTP واحد في الوحدة |
| ملف XBRL رسمي | **لا يُنتَج** — المُصدِّر الرسمي يرفض دائمًا برسالة واضحة |
| تعديل محاسبي | **صفر** — لا كتابة في أي جدول محاسبي |
| قفل فترة / سنة مالية | **بلا مساس** — اللقطة لا تقفل شيئًا |
| تأثير على وحدات أخرى | **صفر** — الرواتب، المستحقات، الشيكات، المخزون بلا تغيير |

## 3. ما تم تنفيذه

### قاعدة البيانات — ترحيل إضافي بحت

`20260819120000_add_xbrl_readiness_foundation` — ستة جداول جديدة، بلا `ALTER` واحد على جدول قائم،
وبلا سطر بيانات واحد يُقرأ أو يُعدَّل:

| الجدول | الدور |
|--------|-------|
| `xbrl_taxonomies` | سجلّ التصنيفات المستقبلية (`isOfficial` مقفول للكتابة) |
| `xbrl_concepts` | مفاهيم التصنيف (نوع البيانات، الرصيد، الفترة، القائمة، الشجرة) |
| `xbrl_account_mappings` | ربط دليل الحسابات بالمفاهيم |
| `xbrl_statement_mappings` | ربط بنود القوائم المالية بالمفاهيم |
| `xbrl_reporting_contexts` | الكيان والفترة والمقارنة والعملة واللغة |
| `xbrl_snapshots` | لقطات إصدار مالي غير قابلة للتعديل |

**التراجع المنطقي:** إسقاط الجداول الستة بترتيب عكسي للاعتماديات يعيد القاعدة إلى حالتها السابقة
بالضبط. لا يوجد ما يُستعاد من بيانات محاسبية لأن الحزمة لم تكتب فيها شيئًا.

النموذج `Account` اكتسب علاقة عكسية واحدة (`xbrlMappings`) — لا عمود جديد على جدول `accounts`.

### الطبقة الخلفية

`backend/src/modules/xbrl/` — راجع `README.md` داخل الوحدة للتفاصيل الكاملة والبنية.

* **محرّك التحقق** دوال صافية بلا Prisma: يُختبَر بمدخلات مصنوعة يدويًا، ولا يستطيع بحكم بنيته أن
  يكتب شيئًا.
* **الأرصدة** تأتي من `financialService.getTrialBalance` — ميزان المراجعة نفسه الذي يعرضه المركز
  المالي. لا استعلام محاسبي جديد، فلا مصدرا حقيقة لنفس الرقم.
* **اللقطة** تعرض `create` / `list` / `getById` فقط، والراوتر لا يحمل `PATCH`/`PUT`/`DELETE` على
  `/snapshots` إطلاقًا.
* **بنية التصدير** `FinancialReportingExporter` + مُصدِّران: `InternalPreviewExporter` (معاينة
  داخلية موسومة صراحةً بأنها غير رسمية) و`XbrlExporter` (حاجز يرفض دائمًا في v1).

### الصلاحيات

`xbrl.read` · `xbrl.manage` · `xbrl.snapshot` — ثلاثة مفاتيح، مستقلة عن `transactions.*`
و`finreports.*`. تُمنح كاملة لـ`SYSTEM_ADMIN` و`GENERAL_MANAGER` و`ACCOUNTANT`.

### الواجهة

صفحة `/xbrl-readiness` بخمسة تبويبات (نظرة عامة · ربط الحسابات · ربط القوائم · التحقق · اللقطات)،
عربية RTL، مبنية على ExplorerKit.

**خارج الشريط الجانبي عمدًا** — تُفتح من زرّ في رأس صفحة «المحاسبة»، كما تُفتح بقية الشاشات
التحليلية الداخلية. أداة إعداد تُستعمل مرّات معدودة في السنة لا تستحق عنصرًا دائمًا في القائمة.

## 4. قواعد التحقق

خمس عشرة قاعدة بأكواد ثابتة (`ACC-*`, `RPT-*`, `MAP-*`, `EXP-*`) — الجدول الكامل في
`backend/src/modules/xbrl/README.md`.

**نتيجة التحقق تقرير لا قفل:** خطأ `ERROR` هنا لا يمنع ترحيل قيد ولا اعتماد فاتورة ولا صرف راتب.
قيد تصميمي صريح.

**الأكواد ثابتة للأبد:** اللقطات القديمة تُقرأ بها. القاعدة الجديدة تأخذ كودًا جديدًا، ولا يُعاد
تعريف كود قائم.

## 6. المطلوب للمرحلة الثانية

عند نشر ملفات ومواصفات QAYD الرسمية، يُضاف ما يلي **بلا إعادة بناء أي شيء**:

1. مستورد التصنيف الرسمي — الملف الوحيد الذي يحقّ له ضبط `isOfficial = true`.
2. المفاهيم الرسمية — تُملأ من ملف التصنيف لا من قائمة مكتوبة يدويًا.
3. قواعد التحقق الرسمية — دوال جديدة بأكواد جديدة؛ القواعد القائمة لا تُمسّ.
4. ربط الشركة والحسابات — بيانات لا كود.
5. توليد مستند XBRL — يُملأ جسم `XbrlExporter.export`.
6. التحقق من المخطط (Schema validation).
7. حزمة تصدير خاصة بـQAYD — مُصدِّر جديد يُسجَّل في `EXPORTERS`.
8. تكامل API — **فقط** إذا وُجد API رسمي وموثَّق.

نقطة الاستئناف الدقيقة: `backend/src/modules/xbrl/export/exporter.ts` →
`XbrlExporter.unavailableReason`.

---

## 7. ما بقي معلَّقًا لعدم توفر مواصفات QAYD

* أكواد المفاهيم الرسمية وأسماء الـnamespaces.
* قواعد التحقق التي تفرضها الجهة (حقول إلزامية، تجميعات، dimensions).
* بنية حزمة التقديم وصيغتها (XBRL / iXBRL / ZIP).
* آلية التقديم: ملف يُرفع يدويًا أم API.
* متطلبات التوقيع أو الاعتماد الإلكتروني.
* الخريطة المرجعية بين دليل حسابات المقاولات ومفاهيم التصنيف.

كل بند أعلاه **غير مُخمَّن عمدًا**. تخمينه يعني بناء ربط سيُعاد بناؤه، وشاشة تعلّم المستخدم أرقامًا
خاطئة، ووثيقة تدّعي جاهزية لم تُختبَر.

## 8. الخطوة التالية التشغيلية

الشاشة تعمل اليوم على قاعدة التطوير وتعرض بحق: **صفر حسابات مربوطة**، ولا تصنيف مفعَّل، ولا سياق
تقرير. أول خطوتين لأي استعمال فعلي:

1. إنشاء **سياق تقرير** (السنة المالية، الفترة، العملة، الكيان) — بدونه تظهر القاعدة `RPT-001` كخطأ.
2. إنشاء **تصنيف داخلي** (`INTERNAL`) وتفعيله، ثم إدخال المفاهيم التي نريد الربط بها مؤقتًا.

كلاهما إعداد بيانات لا تطوير، ولن يُهدر عند وصول التصنيف الرسمي: الربط اليدوي يبقى، ويُعاد توجيهه
إلى المفاهيم الرسمية بتحديث `conceptId` لا بإعادة بناء.
